## Press Release

### N-Body Gravitational Simulation

**For** users exploring physics simulations in the browser
**Who** want to see emergent behavior from simple gravitational rules
**The** N-Body Simulation
**Is a** new interactive simulation mode
**That** lets users observe and interact with gravitational attraction between particles
**Unlike** the basic particle system (E2.2) which only has external forces like gravity
**Our solution** calculates particle-to-particle gravitational forces on the GPU, enabling hundreds of bodies to interact in real-time

---

Users can now witness the mesmerizing dance of celestial mechanics right in their browser. When launching the N-Body simulation, particles attract each other based on their mass and distance - just like planets, stars, and galaxies in space. Watch as particles form orbits, spiral inward, or slingshot past each other in complex trajectories.

The simulation is fully interactive: click anywhere in the scene to spawn new particles and see how they disrupt or join the existing system. Create binary star systems, watch particle clouds collapse under their own gravity, or experiment with different initial conditions to see what patterns emerge.

**Q: How does a user access this simulation?**
A: NEEDS DECISION - This depends on whether we have a simulation selector UI by this point. Options:

**Q: What does the user see when they first load the simulation?**
A: The user sees an initial distribution of particles (e.g., 50-200 particles) that immediately begin attracting each other. The default setup should produce visually interesting behavior within the first few seconds.

**Q: How does click-to-spawn work?**
A: The user clicks somewhere on the canvas. A new particle appears at that position (projected into 3D space at a reasonable depth). The particle has some default mass and zero initial velocity (or small random velocity).

**Q: Can users adjust mass or velocity when spawning?**
A: NOT in V1. Spawned particles use default values. Mass/velocity customization is deferred to M3 (Interactions).

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- Particle deletion (deferred to M3)
- Adjustable mass per particle (deferred to M3)
- Initial velocity control when spawning (deferred to M3)
- Collision between particles (deferred to M4 - E4.1)
- Different colored particles based on mass (deferred to M5)
- Preset scenarios (e.g., "solar system", "galaxy") (deferred to M5)
- Pause/reset controls (deferred to M3 - E3.1)

**Q: What's the minimal version that still delivers the core benefit?**
A:
- N-body gravitational force calculation in compute shader
- Visual rendering of particles moving under mutual attraction
- Click anywhere to add a new particle
- That's it. No UI controls, no presets, no collision.

**Q: What would make us cut scope further if needed?**
A: If time-constrained, we could defer click-to-spawn (E2.3.2) and ship only the gravitational attraction (E2.3.1). Spawning could be done programmatically via console or deferred entirely.

**Q: What are we deferring to future iterations?**
A:
- Particle-particle collision (M4)
- Adjustable simulation parameters via UI (M3)
- Multiple simulation types with selector (M5)
- Visual polish like trails, glow, velocity-based coloring (M5)

### Technical Constraint FAQs

**Q: What existing system capabilities does this depend on?**
A:
- E2.1: GPU Compute Pipeline (must be complete)
- E2.2: Basic particle simulation with position/velocity buffers (must be complete)
- E1.1: Camera system for viewing the scene (must be complete)
- E1.3: Instanced rendering to draw particles (must be complete)

**Q: What new capabilities need to be built?**
A:
- N-body force calculation in compute shader (O(n²) algorithm)
- Mouse-to-world-space coordinate conversion for spawning
- Dynamic particle count (buffer resizing or pre-allocated max)

**Q: Are there performance constraints?**
A: Yes. N-body is O(n²) - every particle checks every other particle. For learning purposes, this is acceptable up to ~1000-2000 particles. Beyond that, we'd need spatial optimizations (Barnes-Hut, etc.), which is out of scope.

**Q: What integration method should be used?**
A: NEEDS RESEARCH - This connects to open decision TD9 in PROJECT_PLAN.md. Options are Euler, Verlet, or RK4. For gravitational simulation, Verlet or RK4 provide better energy conservation, but Euler is simpler to implement first.

**Q: How do we handle particles that get too close?**
A: Use a softening parameter (epsilon) in the gravitational formula to prevent division by near-zero distances. This is standard practice in N-body simulations and prevents particles from "exploding" due to extreme forces.

**Q: How do we handle spawning with a fixed-size GPU buffer?**
A: NEEDS DECISION - Options:
1. Pre-allocate a max buffer (e.g., 10,000 particles) and track active count
2. Recreate buffers when capacity exceeded (simpler but causes frame hitch)

### Edge Cases & Error States

**Q: What happens if the user spawns too many particles?**
A: With pre-allocated buffer approach: spawning fails silently (or shows subtle indicator) when max is reached. With dynamic approach: performance degrades but spawning continues.

**Q: What happens if particles fly off to infinity?**
A: No boundary constraints in N-body - this is physically accurate behavior. If all particles escape, the user sees an empty scene. They can refresh or (in M3) reset the simulation.

**Q: What happens if two particles occupy the same position?**
A: The softening parameter prevents infinite forces. They'll experience a very strong but finite repulsion-like effect due to numerical behavior.

**Q: What happens if the user clicks outside the canvas?**
A: Nothing - click events outside the canvas are ignored.

**Q: What happens if WebGPU compute isn't available?**
A: This should be caught at E2.1 level. If compute shaders don't work, the entire M2 milestone fails gracefully with an error message.

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- Particles visibly attract each other (not just fall down)
- Clicking spawns new particles that participate in the simulation
- The simulation runs at reasonable framerate (30+ FPS) with 200+ particles
- Emergent behaviors are visible (orbits, clustering, slingshots)

**Q: What could go wrong post-launch?**
A:
- Performance issues with larger particle counts
- Numerical instability causing particles to explode or NaN
- Mouse coordinate mapping issues on different screen sizes/DPIs

**Q: Are there compliance or security considerations?**
A: No - this is a local, client-side physics simulation with no data collection or external communication.

## Implementation Scope

### User Stories

- [ ] As a user, I see particles attracting each other gravitationally so that I can observe emergent orbital and clustering behavior
- [ ] As a user, I can click in the scene to spawn a new particle so that I can experiment with different configurations
- [ ] As a user, I see smooth simulation without particles exploding so that the physics feels realistic

### Success Criteria

- [ ] Particles move toward each other when simulation starts (not just downward)
- [ ] Particles can form stable or quasi-stable orbits
- [ ] Clicking on canvas adds a visible new particle
- [ ] New particles participate in gravitational simulation immediately
- [ ] Simulation maintains 30+ FPS with 200 particles
- [ ] No NaN or infinity values cause visual glitches

### Known Compromises

Things we're intentionally deferring or accepting as shortcuts:

- [ ] O(n²) algorithm limits practical particle count to ~1000-2000 - acceptable for learning project
- [ ] No particle collision - particles pass through each other (deferred to M4)
- [ ] Fixed mass for all particles - no mass variation (deferred to M3)
- [ ] No UI controls for gravity strength, softening, etc. - hardcoded values (deferred to M3)
- [ ] Click spawns with default values only - no velocity/mass control (deferred to M3)
