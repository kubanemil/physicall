## Press Release

**For** developers and physics enthusiasts using Physicall
**Who** want particles to interact physically rather than passing through each other
**The** Collision Detection system
**Is a** new capability in the physics simulation
**That** makes particles bounce off each other realistically, enabling dense, interactive particle scenes
**Unlike** the current state where particles pass through each other and only respond to gravity and floor boundaries
**Our solution** implements GPU-accelerated particle-particle collision with spatial hashing for efficient broad-phase detection, handling thousands of colliding particles in real-time

---

Physicall now supports real particle collisions. When particles approach each other, they detect contact and respond with physically plausible bouncing and separation — no more ghosting through neighbors. Users can spawn clusters of particles and watch them pile up, scatter apart on impact, and form natural resting configurations against each other and the floor. The simulation stays responsive even with thousands of particles thanks to a spatial hashing broad-phase that avoids checking every particle pair, keeping collision detection fast as particle counts grow.

## FAQ

### Customer Experience

Q: How does a user see collisions in action?
A: Immediately. With the existing particle simulation running, particles that were previously passing through each other now bounce off one another. Users can spawn particles (Shift+click) and watch them collide, pile up on the floor, and push each other around.

Q: What does a collision look like?
A: When two particles overlap, they separate and exchange velocity based on their masses — similar to billiard ball physics. Particles sliding along the floor will stack and settle naturally rather than occupying the same space.

Q: Do collisions work with the existing interactions?
A: Yes. Dragging a particle (left-click drag) into others will push them apart. Spawning particles into a crowd causes chain reactions. Gravity, time scale, and pause/resume all work as before — collisions simply add another layer of physical interaction.

Q: Does collision affect performance?
A: Users will see the FPS impact in the stats display (Ctrl+Y). With spatial hashing, performance scales much better than brute-force — the system handles thousands of colliding particles while staying interactive. Very dense scenes (many particles in a small area) will be more expensive than spread-out scenes.

Q: Are particle sizes visible?
A: Particles already render as spheres with a fixed radius. Collision detection uses the same radius, so what the user sees matches what the physics simulates.

### Scope & Non-Goals

Q: What is explicitly NOT included in V1?
A: Particle-wall collisions beyond the existing floor boundary. No arbitrary static geometry (boxes, ramps, walls). No particle-particle friction or rotation. No soft-body or deformable collision response. No collision sound effects or visual feedback (sparks, flashes). No user-adjustable restitution (bounciness) slider.

Q: What's the minimal version that still delivers the core benefit?
A: Particle-particle collision detection and response with basic elastic collision. Even without spatial hashing, this delivers the visible outcome — particles bounce off each other. Spatial hashing is a performance optimization that allows it to scale.

Q: What would make us cut scope further if needed?
A: Drop spatial hashing and ship with O(n²) brute-force collision. It works correctly for small particle counts (~100-500). Spatial hashing can be added in a follow-up.

Q: What are we deferring to future iterations?
A: Friction and angular momentum, collision with arbitrary geometry, user-adjustable bounciness/restitution coefficient, and collision event callbacks (for future sound/visual effects).

### Technical Constraint FAQs

Q: What existing system capabilities does this depend on?
A: The GPU compute pipeline (E2.1) that runs physics each frame, the particle data structure (position, velocity, mass, radius stored in GPU buffers), and the existing boundary collision with the floor (E2.2).

Q: What new capabilities need to be built?
A: Two main things: (1) A collision detection and response pass in the compute shader that detects overlapping particles and applies impulse-based separation. (2) A spatial hash data structure on the GPU that partitions particles into grid cells so only nearby particles are checked against each other.

Q: How does spatial hashing work on the GPU?
A: Each particle is assigned to a grid cell based on its position. A hash table maps cell indices to particle lists. During collision detection, each particle only checks against particles in its own cell and the 26 neighboring cells (3D grid). This reduces checks from O(n²) to approximately O(n) for uniformly distributed particles.

Q: What collision response method should be used?
A: Impulse-based elastic collision. When two particles overlap: (1) separate them so they no longer overlap (positional correction), (2) calculate and apply impulse to exchange velocity based on relative velocity and masses. This is simple, stable, and physically intuitive.

Q: Are there concerns about particles tunneling through each other at high speeds?
A: Yes, if a particle moves fast enough to pass completely through another in a single frame, the collision will be missed. For V1, this is acceptable — the time scale slider can slow the simulation if needed. Continuous collision detection (CCD) is deferred.

Q: How many collision iterations per frame?
A: A single pass. Multiple iterations (Jacobi/Gauss-Seidel style) would improve stability for tightly packed scenarios but add complexity. One pass is sufficient for the learning goals and delivers visually correct behavior for most scenes.

### Edge Cases & Error States

Q: What happens when many particles are spawned in the same location?
A: The positional correction step pushes overlapping particles apart. With many overlaps, particles will "explode" outward in a burst. This is physically reasonable and visually interesting — not a bug.

Q: What happens if particles are moving very fast?
A: At extreme velocities, particles may tunnel through each other (missed collision). The time scale slider mitigates this. No special handling in V1.

Q: What happens when particles pile up against the floor?
A: Particles stack naturally. The floor collision (existing) prevents them from falling through, and particle-particle collision prevents them from overlapping. Dense piles may jitter slightly with a single collision pass — acceptable for V1.

Q: What if spatial hash cells are too large or too small?
A: Cell size should be roughly 2x the particle radius for optimal performance. If all particles cluster in one cell, performance degrades to O(n²) for that cluster. Fixed cell size is acceptable for V1 since all particles have the same radius.

### Business & Operational FAQs

Q: How will we know if this is successful?
A: Particles visibly bounce off each other instead of passing through. Dense particle scenes (500+ particles) remain interactive (>30 FPS). The simulation looks physically plausible — particles pile up, scatter, and settle.

Q: What could go wrong post-launch?
A: Performance regression with large particle counts if spatial hashing isn't implemented efficiently. Particles jittering or "vibrating" in dense piles due to single-pass collision. Energy gain (particles speeding up) from numerical issues in collision response.

Q: What's the key learning outcome?
A: Understanding GPU-based collision detection — spatial partitioning on the GPU, parallel collision response, and the tradeoffs between accuracy and performance in real-time physics.

## Implementation Scope

### Current State → End State

| Current State | End State |
| --- | --- |
| Particles pass through each other — no physical interaction between particles | Particles collide and bounce off each other with impulse-based response |
| Only floor boundary collision exists | Floor collision + particle-particle collision both active |
| N-body gravity is O(n²) brute-force, limiting practical particle counts | Spatial hash enables efficient neighbor lookups, collision scales to thousands of particles |

### User Stories

- [ ] As a user, I see particles bounce off each other instead of passing through so that the simulation feels physically real
- [ ] As a user, I can spawn particles into a group and see them push each other apart so that interactions feel tangible
- [ ] As a user, I can drag a particle through others and watch them scatter so that mouse interaction feels impactful
- [ ] As a user, I can simulate 1000+ colliding particles at interactive frame rates so that I can explore dense scenes
- [ ] As a user, particles pile up on the floor and on top of each other so that gravity and collision work together naturally

### Success Criteria

- [ ] Particles detect overlap and separate — no two particles occupy the same space
- [ ] Collision response is impulse-based — particles exchange velocity on contact
- [ ] Existing features (gravity, floor bounce, mouse drag, spawn, delete, pause, reset) continue to work
- [ ] 1000+ particles with collisions run at >30 FPS (visible in stats display)
- [ ] Spatial hashing reduces collision checks from O(n²) to approximately O(n)
- [ ] Particle piles look stable — no visible energy gain or explosive jittering

### Known Compromises

- [ ] Single collision pass per frame rather than iterative solving — may cause jitter in dense piles, but simpler to implement and understand
- [ ] No continuous collision detection (CCD) — fast particles may tunnel through each other, mitigated by time scale slider
- [ ] Fixed spatial hash cell size (2x particle radius) rather than adaptive — all particles share the same radius so this is fine for now
- [ ] No friction or angular momentum — collisions are purely elastic with no tangential response
- [ ] No restitution (bounciness) control — fixed coefficient, user-adjustable slider deferred

### Open Questions / Needs Research

- [ ] How to build a GPU spatial hash in WGSL — what data structures are needed (cell arrays, particle index lists, atomic counters)?
- [ ] Should the spatial hash be rebuilt every frame, or incrementally updated?
- [ ] What's the best buffer layout for the spatial hash — structure of arrays vs array of structures?
- [ ] Should collision detection and response be separate compute passes or combined into one?
- [ ] What restitution coefficient to use as default (0.8 = slightly inelastic is typical)?
