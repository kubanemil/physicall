## Press Release

**For** developers learning WebGPU and physics simulation
**Who** want to run physics calculations on the GPU for massive parallelism
**The** GPU Compute Pipeline
**Is a** foundational capability enabling GPU-accelerated simulation
**That** allows thousands of particles to update their positions in parallel every frame
**Unlike** CPU-based simulation loops that process particles sequentially
**Our solution** uses WebGPU compute shaders to leverage GPU parallelism, with seamless buffer sharing between compute and render passes

---

Physicall now supports GPU compute shaders, unlocking the ability to run physics simulations entirely on the GPU. Developers can dispatch compute workloads that process particle data in parallel—what would take milliseconds on a CPU for thousands of particles now happens in microseconds on the GPU.

The compute pipeline integrates directly with the existing render pipeline through shared GPU buffers. Particle positions updated by the compute shader are immediately available for rendering without any CPU-GPU data transfer. This zero-copy architecture means you can simulate and render 10,000+ particles at 60fps, setting the foundation for gravity, collisions, and constraint-based simulations in future milestones.

## FAQ

### Customer Experience

**Q: How does a developer use the compute pipeline?**
A: The compute pipeline runs automatically as part of the simulation loop. Each frame: (1) compute shader dispatches, updating particle positions in the GPU buffer, (2) render pass draws particles using the same buffer. Developers don't need to manually trigger compute—it's integrated into the frame loop.

**Q: What does the user see when compute is working?**
A: Particles will visibly move or change based on the compute shader logic. Initially, this might be as simple as particles drifting in a direction, proving that compute output feeds into rendering. The visual feedback confirms the pipeline is functional.

**Q: How do I know if compute shaders are actually running vs CPU fallback?**
A: NEEDS RESEARCH - Determine if wgpu provides diagnostic info about compute dispatch. May need to add timing instrumentation or GPU query support.

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- No physics logic (gravity, forces, integration)—that's E2.2
- No collision detection—that's M4
- No user controls to modify compute parameters—that's M3
- No particle spawning/deletion—just a fixed buffer of particles

**Q: What's the minimal version that delivers the core benefit?**
A: A compute shader that modifies particle positions in some visible way (e.g., moving all particles by a fixed offset each frame), with those changes rendered immediately. This proves: compute dispatch works, buffer binding works, compute-to-render data flow works.

**Q: What would make us cut scope further if needed?**
A: If buffer sharing proves complex, we could start with compute writing to a separate buffer and manually copying to render buffer. This adds a copy but isolates concerns.

**Q: What are we deferring to future iterations?**
A:
- Double-buffering for compute (ping-pong buffers)—needed for proper physics but not for proving compute works
- Workgroup optimization—start with naive dispatch, optimize later
- Compute shader hot-reloading—nice to have, not essential

### Technical Constraint FAQs

**Q: What existing system capabilities does this depend on?**
A:
- WebGPU device/queue initialization (E0.2) ✅
- Render pipeline with instanced rendering (E1.3) ✅
- GPU buffer containing particle instance data (E1.3) ✅

**Q: What new capabilities need to be built?**
A:
- Compute pipeline creation (bind group layout, pipeline layout, compute pipeline)
- Compute shader (.wgsl file) with proper bindings
- Buffer configuration for both compute and render access (storage + vertex usage)
- Compute dispatch integration into frame loop

**Q: Are there performance, scale, or data constraints?**
A: Initial target is 10,000 particles. Compute shaders should handle this easily. The constraint is more about buffer size limits and bind group configurations. NEEDS RESEARCH - Verify wgpu buffer size limits for web target.

**Q: What's the simplest implementation that delivers the PR outcome?**
A: Single compute shader with one storage buffer binding. Shader reads particle positions, applies trivial transformation (e.g., `position.x += 0.001`), writes back. Dispatch with workgroup size 64, dispatch count = particle_count / 64.

### Edge Cases & Error States

**Q: What happens if compute shader compilation fails?**
A: Should surface WGSL compilation errors to browser console with line numbers. This is critical for debugging. Existing shader error handling patterns from render shaders should apply.

**Q: What happens if buffer binding fails?**
A: wgpu validation layer will catch mismatched bind group layouts. Errors appear in console. No graceful fallback—this is a development error, not runtime.

**Q: What happens if compute dispatch hangs or takes too long?**
A: Browser's GPU watchdog will terminate the context. For development, keep particle counts reasonable. NEEDS DECISION - Should we add a max particle count limit initially?

**Q: What if the GPU doesn't support compute shaders?**
A: WebGPU requires compute shader support—it's a core feature. Any browser with WebGPU will have compute. No fallback needed.

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- Compute shader compiles and dispatches without errors
- Particles visibly move/change each frame due to compute output
- Frame rate remains stable (60fps target) with 10,000 particles
- No CPU-GPU buffer transfers in the frame loop (verified via timing or profiler)

**Q: What could go wrong post-launch?**
A:
- Different browsers may have subtle differences in WGSL validation
- Memory alignment issues with buffer layouts
- Workgroup size assumptions that don't hold on all GPUs

**Q: Does this require changes to support/ops processes?**
A: No—this is foundational infrastructure, not user-facing features.

**Q: Are there compliance or security considerations?**
A: No—compute shaders run in browser sandbox like all WebGPU content.

## Implementation Scope

### Current State → End State

| Current State | End State |
|---------------|-----------|
| Particles render but positions are static (set once at init) | Particles render with positions updated by GPU compute each frame |
| Only render pipeline exists | Both compute and render pipelines exist |
| Particle buffer has vertex usage only | Particle buffer has storage + vertex usage for compute read/write |
| Frame loop: render pass only | Frame loop: compute dispatch → render pass |

### User Stories

- [ ] As a developer, I can create a compute pipeline with proper bind group layout so that compute shaders can access GPU buffers
- [ ] As a developer, I can write a WGSL compute shader that reads and writes to a storage buffer so that particle data can be modified on GPU
- [ ] As a developer, I can dispatch compute work before render pass so that particle positions update each frame
- [ ] As a user, I see particles moving on screen, proving that compute output feeds into rendering

### Success Criteria

- [ ] Compute shader compiles without errors on Chrome, Firefox (if WebGPU enabled)
- [ ] Particles visibly move each frame due to compute shader modifications
- [ ] 10,000 particles maintain 60fps on mid-range GPU (e.g., integrated graphics)
- [ ] No `buffer.map()` or CPU data transfers in the per-frame code path
- [ ] Compute and render use the same GPU buffer (verified by code inspection)

### Known Compromises

- [ ] Single-buffered compute (no ping-pong) - acceptable for simple per-particle updates; will need double-buffering for physics that reads neighbor data
- [ ] Hardcoded workgroup size (64) - may not be optimal for all GPUs; optimization deferred
- [ ] No compute shader hot-reload - must rebuild WASM to change compute logic; acceptable for learning project

### Open Questions / Needs Research

- [ ] What buffer usage flags are needed for compute + render sharing in wgpu?
- [ ] How to structure bind group layout for compute pipeline?
- [ ] What's the recommended workgroup size for web targets?
- [ ] How to measure/verify compute dispatch timing for performance validation?
- [ ] Does wgpu require explicit barriers between compute and render, or is queue submission sufficient?
