## Press Release

### Primitive Rendering

**For** developers building physics simulations
**Who** need to visualize particles, connections, and objects in 3D
**The** Primitive Rendering system
**Is a** core rendering capability
**That** provides the visual building blocks for any simulation
**Unlike** the current state where only a basic triangle can be rendered
**Our solution** offers efficient GPU-based rendering of points, lines, and spheres with proper sizing and depth

---

Physicall now supports rendering the three fundamental primitives needed for physics visualization: points, lines, and spheres.

Developers can render thousands of particles as sized points, draw debug lines to visualize forces and constraints, and display spheres for particle-based simulations that need visible volume. Each primitive type is rendered efficiently on the GPU, setting the foundation for the instanced rendering and compute-based particle systems that follow.

## FAQ

### Customer Experience

**Q: How does a developer use these primitives?**
A: Through Rust APIs exposed to the renderer. Developers specify primitive type, positions (as GPU buffer or data), and visual properties (size, color). The renderer handles batching and draw calls.

**Q: What does the happy path look like?**
A:
1. Developer creates a renderer with WebGPU context
2. Developer adds primitives (points/lines/spheres) with position data
3. Renderer draws all primitives each frame with proper depth sorting
4. Developer sees the visualization on the canvas

**Q: How do primitives interact with the existing camera system (E1.1)?**
A: Primitives are rendered in world space and transformed by the camera's view-projection matrix. Orbit, zoom, and reset all work with primitives.

**Q: What visual properties can be controlled?**
A: For V1: position and uniform size for points, start/end positions for lines, position and radius for spheres. Color will be uniform per primitive type initially.

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- Per-instance colors (deferred to M2 when compute buffers feed render)
- Anti-aliased lines
- Textured spheres
- Billboard sprites (alternative to spheres)
- Variable line thickness

**Q: What's the minimal version that delivers the core benefit?**
A: Points with uniform size, single-segment lines, and basic sphere meshes. All with a single uniform color per draw call.

**Q: What would make us cut scope further?**
A: If sphere mesh generation proves complex, we could defer spheres to E1.3 (Instanced Rendering) since they require mesh data. Points and lines are simpler and higher priority.

**Q: What are we deferring to future iterations?**
A:
- Per-instance colors → M2 (when particle data comes from compute)
- Instanced sphere rendering with 10K+ objects → E1.3
- Velocity-based coloring → M5

### Technical Constraints

**Q: What existing capabilities does this depend on?**
A:
- WebGPU device and surface (E0.2)
- Basic render pipeline (E0.3)
- Camera system with view-projection matrix (E1.1)

**Q: What new capabilities need to be built?**
A:
- Point primitive pipeline (or use vertex shader point sizing)
- Line primitive pipeline
- Sphere mesh generation (icosphere or UV sphere)
- Uniform buffers for primitive properties

**Q: Are there performance constraints?**
A: Should handle 1,000+ points and 100+ lines without frame drops. Sphere count will be limited until E1.3 (instancing). This is a learning project, so production-grade performance is not required.

**Q: What's the simplest implementation?**
A:
- Points: Use WebGPU point primitive topology with vertex shader point sizing
- Lines: Use line-list primitive topology
- Spheres: Generate icosphere mesh once, render with basic vertex/fragment shaders

### Edge Cases & Error States

**Q: What happens if no primitives are added?**
A: Renderer draws nothing (clear color only). No error.

**Q: What happens with zero-size points or zero-radius spheres?**
A: Clamp to minimum visible size (1 pixel for points, small epsilon for spheres).

**Q: What if sphere mesh generation fails?**
A: Fall back to rendering a point at the sphere center. Log warning.

**Q: What are the boundary conditions?**
A:
- Maximum points/lines: Limited by GPU buffer size, but practically unlimited for learning purposes
- Sphere radius: Positive non-zero float
- Point size: 1-64 pixels (WebGPU typical limit)

### Success Metrics

**Q: How will we know if this is successful?**
A:
- Can render 1,000 points at 60fps
- Can render debug lines (e.g., coordinate axes, bounding box)
- Can render 10+ spheres with visible depth ordering
- Primitives work correctly with camera orbit/zoom

**Q: What could go wrong post-implementation?**
A:
- Depth fighting between overlapping primitives
- Point size not working on certain GPUs (WebGPU compatibility)
- Sphere winding order issues causing invisible faces

## Implementation Scope

### Current State → End State

| Current State | End State |
|---------------|-----------|
| Only a single hardcoded triangle can be rendered | Developer can render points, lines, and spheres |
| No control over primitive properties | Size, position, and basic color can be specified |
| No debug visualization capability | Lines available for visualizing axes, bounds, forces |
| No volumetric particle representation | Spheres can represent particles with physical radius |

### User Stories

- [ ] As a developer, I can render points/particles with configurable size so that I can visualize particle positions
- [ ] As a developer, I can render line segments so that I can debug forces, constraints, and boundaries
- [ ] As a developer, I can render spheres so that I can visualize particles with physical volume
- [ ] As a developer, all primitives respect the camera view so that I can orbit and zoom the visualization

### Success Criteria

- [ ] 1,000 points render at 60fps
- [ ] Lines are visible and correctly positioned in 3D space
- [ ] Spheres have correct depth ordering (no z-fighting)
- [ ] All primitives transform correctly with camera movement
- [ ] Point size is adjustable (at least 1-20 pixel range)

### Known Compromises

- [ ] Uniform color per draw call — Per-instance colors deferred until compute buffers exist in M2
- [ ] Non-instanced sphere rendering — Will be slow with many spheres, but E1.3 adds instancing
- [ ] Simple sphere mesh — Low polygon count acceptable for learning project

### Open Questions / Needs Research

- [ ] What sphere mesh subdivision level balances visual quality vs vertex count?
- [ ] Does WebGPU point primitive support point sizing on all target browsers (Chrome primary)?
- [ ] Should lines use line-list or line-strip topology for debug visualization?
- [ ] How to handle depth buffer configuration for proper primitive sorting?
