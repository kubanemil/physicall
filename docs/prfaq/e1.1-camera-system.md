## Press Release

### Interactive 3D Camera Controls

**For** users exploring physics simulations in Physicall
**Who** need to view simulations from different angles and distances
**The** Camera System
**Is a** core navigation capability
**That** lets users intuitively explore 3D simulations using familiar mouse controls
**Unlike** a fixed viewpoint that limits observation
**Our solution** provides smooth orbit, zoom, and reset controls that feel natural to anyone who's used 3D software

---

Physicall now features a fully interactive camera system that puts you in control of your viewing experience. Click and drag anywhere on the canvas to orbit around the simulation—rotate left, right, up, and down to observe particles, forces, and collisions from any angle. Use your scroll wheel to zoom in for close-up detail or pull back for a full overview of the action.

Lost your bearings? A single reset command snaps you back to the default view instantly. Whether you're tracking a single particle's trajectory or observing emergent patterns in a thousand-body simulation, the camera stays responsive and smooth, never getting in the way of your exploration.

## FAQ

### Customer Experience

**Q: How does a user access camera controls?**
A: Controls are always active on the simulation canvas. No mode switching required—just click and drag to orbit, scroll to zoom.

**Q: What does the happy path look like?**
A:
1. User loads a simulation (from M0/M2)
2. User sees the default camera view (positioned to show the full simulation)
3. User clicks and drags on canvas → camera orbits around center
4. User scrolls up/down → camera zooms in/out
5. User presses reset (key or button) → camera returns to default view

**Q: What happens if the user drags outside the canvas?**
A: Drag continues tracking until mouse button is released, even if cursor leaves canvas bounds. This prevents jarring camera jumps.

**Q: How does this interact with future mouse interactions (particle dragging in M3)?**
A: NEEDS DECISION - Options:
- Left-click orbits, right-click/modifier+click for particle interaction
- Separate "camera mode" vs "interaction mode" toggle
- Context-sensitive (click on particle vs empty space)

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- First-person (FPS-style) camera
- 2D pan/zoom mode
- Multiple camera presets/saved views
- Camera animation/flythrough
- Touch/gesture support
- Keyboard-based camera movement (WASD)

**Q: What's the minimal version that still delivers the core benefit?**
A: Orbit + zoom only, with hardcoded default view (no reset button). Reset can be achieved by page refresh.

**Q: What would make us cut scope further if needed?**
A: Cut E1.1.3 (reset functionality) and ship orbit + zoom only.

**Q: What are we deferring to future iterations?**
A:
- Camera collision (preventing camera from going inside objects)
- Smooth easing/momentum on camera movements
- Configurable sensitivity settings
- Camera constraints (limiting orbit angles)

### Technical Constraint FAQs

**Q: What existing system capabilities does this depend on?**
A:
- M0 must be complete (WebGPU initialization, render pipeline)
- A scene with something to look at (even just the hello triangle from E0.3)

**Q: What new capabilities need to be built?**
A:
- View/projection matrix calculation
- Mouse event handling (in WASM or JS→WASM bridge)
- Uniform buffer for camera matrices (if not already present)

**Q: Are there performance constraints?**
A: Camera matrix updates must happen per-frame without blocking. Since it's just matrix math, this should be trivial.

**Q: What's the simplest implementation approach?**
A: Orbit camera using spherical coordinates (radius, theta, phi) with a fixed look-at target at origin.

### Edge Cases & Error States

**Q: What happens if the user zooms too far in?**
A: Camera should have minimum distance limit to prevent clipping through the look-at target or inverting.

**Q: What happens if the user zooms too far out?**
A: Camera should have maximum distance limit to prevent the simulation becoming invisibly small.

**Q: What happens if the user rotates to extreme vertical angles?**
A: Gimbal lock prevention needed—limit vertical rotation to avoid flipping upside down (common: clamp to ±89°).

**Q: What is the default camera position?**
A: NEEDS DECISION - Should be positioned to show typical simulation bounds. Suggested: 45° elevation, 45° azimuth, distance auto-calculated or fixed at reasonable default.

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- Camera responds immediately to input (no perceptible lag)
- Users can view any part of the simulation from any angle
- No visual artifacts (clipping, z-fighting) during normal use

**Q: What could go wrong post-launch?**
A:
- Mouse sensitivity feels wrong on different devices/DPIs
- Orbit behavior feels unintuitive (inverted vs natural)
- Conflicts with browser's own scroll behavior

**Q: Are there compliance or security considerations?**
A: No—purely client-side rendering code.

## Implementation Scope

### Current State → End State

| Current State | End State |
|---------------|-----------|
| Camera is fixed (or doesn't exist yet) | User can orbit camera by dragging mouse |
| No zoom capability | User can zoom with scroll wheel |
| Must refresh page to reset view | User can reset camera with button/hotkey |

### User Stories

- [ ] As a user, I can click and drag on the canvas to orbit the camera around the simulation so that I can view it from any angle
- [ ] As a user, I can scroll to zoom in and out so that I can see detail or get an overview
- [ ] As a user, I can reset the camera to default view so that I can quickly return to a known good position

### Success Criteria

- [ ] Dragging horizontally rotates view left/right around the center
- [ ] Dragging vertically rotates view up/down (with angle limits)
- [ ] Scrolling up zooms in, scrolling down zooms out
- [ ] Zoom has min/max distance limits
- [ ] Reset returns camera to initial position and orientation
- [ ] Camera feels smooth (no stuttering or lag)
- [ ] Works in Chrome (primary browser target)

### Known Compromises

- [ ] No configurable sensitivity - using hardcoded values that feel reasonable (can add settings in M3/M5)
- [ ] No smooth easing/momentum - camera stops immediately when input stops (polish item for later)
- [ ] Fixed look-at target at origin - doesn't track objects or allow panning (good enough for centered simulations)

### Open Questions / Needs Research

- [ ] How to handle camera vs particle interaction conflicts (for M3 planning)
- [ ] Best default camera position for typical simulation bounds
- [ ] Whether to handle inversion preference (some users expect inverted Y-axis)
