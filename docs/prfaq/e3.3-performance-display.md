> **Reference**: E3.3
> **Created**: 2026-02-17
> **Status**: Ready for Implementation

## Press Release

**For** developers and physics enthusiasts using Physicall
**Who** want to understand how their simulation is performing in real-time
**The** Performance Display
**Is a** new capability added to the simulation UI
**That** shows live FPS, frame timing, and simulation statistics at a glance
**Unlike** the current state where users have no visibility into performance
**Our solution** provides a lightweight, always-visible stats overlay that helps users understand the cost of their simulation choices

---

Physicall now shows real-time performance metrics directly in the simulation view. Users can see their current frames per second, frame time in milliseconds, and active particle count — all updated live as the simulation runs. When users spawn more particles, adjust gravity, or change time scale, they can immediately see how those changes affect performance. The stats display is unobtrusive and doesn't interfere with the simulation view or existing controls.

## FAQ

### Customer Experience

Q: How does a user see the performance display?
A: A small stats panel is always visible in a corner of the screen (e.g., top-right), showing FPS, frame time (ms), and particle count. It updates in real-time without any user action required.

Q: What metrics are shown?
A: **FPS** (frames per second), **frame time** (milliseconds per frame), and **particle count** (active particles). FPS and frame time are smoothed/averaged to avoid jittery readings.

Q: Can the user hide the stats display?
A: Yes. The stats panel is toggleable — visible by default, with a keyboard shortcut or button to hide/show it.

Q: How does this interact with the existing particle count in the controls panel?
A: The particle count will be moved from the controls panel to the new stats display with more frequent updates. It will be removed from the controls panel to avoid duplication.

Q: What happens when the simulation is paused?
A: The stats display continues to show metrics. FPS reflects the render loop speed (which still runs for camera interaction). Frame time still updates. Particle count remains static since no particles are spawning/dying.

### Scope & Non-Goals

Q: What is explicitly NOT included in V1?
A: GPU memory usage, GPU compute time breakdown, per-system profiling (physics vs render), graph/chart history of FPS over time, or benchmark modes.

Q: What's the minimal version that still delivers the core benefit?
A: An FPS counter and particle count displayed on screen. Frame time is a nice-to-have but closely derived from FPS.

Q: What are we deferring to future iterations?
A: Performance graphs over time, GPU profiling, configurable stats selection, and detailed per-system timing breakdowns.

### Technical Constraint FAQs

Q: What existing system capabilities does this depend on?
A: The render loop already runs via `requestAnimationFrame`, which provides frame timestamps. `get_particle_count()` is already exported from WASM. The main challenge is computing FPS from frame deltas.

Q: Where should FPS be calculated — Rust/WASM or TypeScript?
A: TypeScript. It already owns the `requestAnimationFrame` loop and has access to frame timestamps. Calculating FPS in TypeScript avoids WASM boundary overhead and keeps the stats logic simple and self-contained.

Q: How should FPS be smoothed to avoid jittery display?
A: Use a rolling average (e.g., exponential moving average or average over last N frames) to produce stable, readable numbers. A common approach is EMA with alpha ~0.1, or averaging the last 60 frames.

Q: Are there performance concerns with the stats display itself?
A: Minimal. Updating a few DOM text nodes per frame is negligible. The display should NOT use canvas overlay rendering — simple HTML/CSS is sufficient and cheaper.

### Edge Cases & Error States

Q: What happens at very low FPS (e.g., <10)?
A: Display still shows the actual FPS value. No special handling needed — the low number itself communicates the problem.

Q: What happens on the first frame before any averaging?
A: Show "--" or "0" until enough frames have accumulated for a meaningful average (typically 1-2 frames).

Q: What if the browser tab is backgrounded?
A: `requestAnimationFrame` throttles when backgrounded. FPS will naturally drop to reflect this. No special handling needed.

### Business & Operational FAQs

Q: How will we know if this is successful?
A: Users (the developer) can observe FPS impact when changing particle count or simulation parameters. The display is readable and stable (not flickering between values).

Q: What could go wrong post-launch?
A: The stats panel could obscure important simulation content. Mitigation: position it in a corner with low opacity or small font, consistent with existing UI style.

## Implementation Scope

### Current State → End State

| Current State | End State |
| --- | --- |
| No FPS visibility — user can't tell if simulation runs at 60fps or 15fps | Live FPS counter visible at all times |
| No frame time display | Frame time in ms shown alongside FPS |
| Particle count buried in controls panel, updates every 10 frames | Particle count in stats overlay, updates every frame (or more frequently) |

### User Stories

- [ ] As a user, I can see the current FPS so that I know how smoothly the simulation is running
- [ ] As a user, I can see frame time in milliseconds so that I can understand per-frame cost
- [ ] As a user, I can see the active particle count in the stats display so that I know the simulation scale
- [ ] As a user, the stats update smoothly without jittering so that the numbers are readable
- [ ] As a user, I can toggle the stats panel on/off so that I can have a clean view when I don't need metrics

### Success Criteria

- [ ] FPS counter is displayed on screen and updates in real-time
- [ ] Frame time (ms) is displayed alongside FPS
- [ ] Particle count is shown in the stats display (removed from controls panel)
- [ ] Values are smoothed/averaged so they don't flicker rapidly
- [ ] Stats panel can be toggled on/off
- [ ] Stats display does not interfere with simulation interaction (camera, particle dragging)
- [ ] Stats display is visually consistent with existing UI controls style, positioned top-right

### Known Compromises

- [ ] FPS calculation in TypeScript rather than Rust — simpler but less precise than GPU-side timing
- [ ] Rolling average smoothing rather than percentile-based stats — good enough for visual feedback
- [ ] Simple toggle (keyboard shortcut or button) rather than granular per-metric visibility

### Decisions Made

- **Toggleable**: Stats panel visible by default, toggle with `Ctrl+Y`
- **FPS in TypeScript**: Calculated in the rAF loop, no WASM involvement
- **Position**: Top-right corner, visually consistent with existing controls panel style
- **Particle count moved**: Removed from controls panel, lives only in stats display
- **Update frequency**: Display values refresh every 500ms (internal tracking every frame, display throttled)

### Open Questions / Needs Research

None — all decisions resolved.

- **Toggle shortcut**: `Ctrl+Y`
- **Update frequency**: Every 500ms (2x per second) — frequent enough to feel responsive, slow enough to be readable without flickering
