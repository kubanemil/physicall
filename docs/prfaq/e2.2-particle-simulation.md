## Press Release

### GPU-Powered Particle Simulation

**For** developers learning physics simulation and GPU computing
**Who** want to see particles interact with forces and boundaries in real-time
**The** Particle Simulation feature
**Is a** core simulation capability
**That** enables thousands of particles to fall, bounce, and respond to adjustable gravity
**Unlike** the current static rendering where objects don't move or interact
**Our solution** runs all physics calculations on the GPU via compute shaders, enabling smooth real-time simulation of thousands of particles

---

Physicall now brings particles to life. When you load the simulation, you'll see particles spawned in the scene immediately begin falling under the influence of gravity. Watch as they accelerate downward, then bounce off the floor boundary, losing some energy with each collision.

Want to experiment? Adjust the gravity slider and see particles respond instantly—crank it up for dramatic falls, dial it down for floaty, moon-like physics, or reverse it entirely. This is your first taste of interactive physics simulation, and everything runs at smooth frame rates thanks to GPU compute shaders handling all the math in parallel.

## FAQ

### Customer Experience

**Q: How do I start the particle simulation?**
A: Load the application and particles will spawn automatically. The simulation begins running immediately—you'll see particles falling right away.

**Q: What controls are available?**
A: A gravity strength slider lets you adjust how strongly particles are pulled downward. This updates in real-time as you drag.

**Q: What happens when particles hit the floor?**
A: Particles bounce off the floor boundary. They'll lose some energy with each bounce (damping), eventually settling if gravity is moderate.

**Q: Can particles go through walls or escape the scene?**
A: V1 only includes a floor boundary. Particles can move freely in X and Z directions. Wall boundaries are deferred to future iterations.

**Q: How many particles will there be?**
A: The initial implementation will spawn a fixed number of particles (target: 1,000-10,000). Dynamic spawning is deferred to E2.3.

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- Particle-particle collisions (deferred to M4)
- Wall boundaries (only floor)
- Dynamic particle spawning/deletion
- Particle trails or visual effects
- Multiple force types (only gravity)

**Q: What's the minimal version that delivers the core benefit?**
A: Particles fall under gravity and bounce off the floor. Even without adjustable gravity, this demonstrates the compute shader pipeline working.

**Q: What would make us cut scope further?**
A: If compute shader debugging proves difficult, we'd implement CPU-side physics first as a reference, then port to GPU.

**Q: What are we deferring to future iterations?**
A:
- N-body gravitational attraction (E2.3)
- Click-to-spawn particles (E2.3)
- Particle-particle collisions (M4)
- Constraint systems (M4)

### Technical Constraint FAQs

**Q: What existing capabilities does this depend on?**
A:
- E2.1: GPU Compute Pipeline must be working (compute shaders can run and results visible in render)
- M1: Instanced rendering must work (to render thousands of particles efficiently)
- Camera system (to view the simulation from different angles)

**Q: What new capabilities need to be built?**
A:
- Position integration compute shader (Euler or Verlet)
- Velocity storage and update
- Floor collision detection and response
- Uniform buffer for simulation parameters (gravity, delta time)
- JS/TS control binding for gravity slider

**Q: Are there performance constraints?**
A: Target is 60fps with 10,000 particles. This should be achievable with GPU compute—the bottleneck is more likely rendering than physics at this scale.

**Q: What integration method should we use?**
A: NEEDS RESEARCH - Project plan lists Euler, Verlet, and RK4 as options. Semi-implicit Euler is simplest and often sufficient for basic particle systems.

### Edge Cases & Error States

**Q: What happens if gravity is set to zero?**
A: Particles maintain their current velocities and drift. This is valid behavior.

**Q: What happens if gravity is negative?**
A: Particles fall upward. This should be allowed—it's fun to experiment with.

**Q: What happens if a particle spawns below the floor?**
A: Initial spawn positions should be above the floor. If somehow below, the collision response should push it back up.

**Q: What happens if delta time is very large (lag spike)?**
A: NEEDS DECISION - Options: (A) Clamp delta time to max value, (B) Use fixed timestep with accumulator, (C) Accept instability on lag. Recommend (A) for V1 simplicity.

**Q: What if WebGPU compute isn't supported?**
A: The existing E0.2.2 error handling should cover this. No simulation runs if WebGPU unavailable.

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- Particles visibly fall and bounce (visual confirmation)
- Gravity slider changes behavior in real-time
- Maintains 60fps with 10,000 particles
- No visual artifacts or physics explosions

**Q: What could go wrong post-launch?**
A:
- Numerical instability causing particles to explode or tunnel through floor
- Performance issues on lower-end GPUs
- Precision issues with single-precision floats

**Q: Are there compliance or security considerations?**
A: None—this is a local browser simulation with no data collection or network access.

## Implementation Scope

### Current State -> End State

| Current State | End State |
|---------------|-----------|
| Static rendered scene with no movement | Particles fall under gravity |
| No physics simulation running | GPU compute shader updates positions each frame |
| No user control over simulation | Gravity slider adjusts simulation parameters |
| Objects pass through boundaries | Particles bounce off floor |

### User Stories

- [ ] As a user, I see particles falling under gravity when the simulation loads
- [ ] As a user, I see particles bounce when they hit the floor boundary
- [ ] As a user, I can adjust gravity strength with a slider and see immediate effect
- [ ] As a developer, I can verify physics runs on GPU (not CPU)

### Success Criteria

- [ ] 10,000 particles render and simulate at 60fps
- [ ] Particles accelerate downward (not constant velocity)
- [ ] Particles bounce off floor with visible energy loss
- [ ] Gravity slider updates simulation in real-time
- [ ] No particles tunnel through the floor
- [ ] No numerical explosion (particles flying off to infinity)

### Known Compromises

- [ ] Only floor boundary in V1 - particles can escape horizontally (keeps collision simple)
- [ ] Fixed particle count - no spawning/deletion (simplifies buffer management)
- [ ] Single force type (gravity) - no wind, attractors, etc. (focused scope)
- [ ] Semi-implicit Euler integration - less accurate than Verlet/RK4 but simpler to implement

### Open Questions / Needs Research

- [ ] Which integration method? (Euler vs Verlet vs RK4) - affects stability and complexity
- [ ] How to handle large delta times on lag spikes?
- [ ] What initial particle distribution? (random box, grid, sphere?)
- [ ] What bounce damping factor feels good? (0.8? 0.5?)
- [ ] Buffer layout for particles - interleaved (pos+vel) or separate buffers?
