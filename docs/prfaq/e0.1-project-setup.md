## Press Release

### Physicall Development Environment

**For** developers learning Rust, WebAssembly, and WebGPU
**Who** want to build GPU-accelerated physics simulations in the browser
**The** Physicall development environment
**Is a** foundational project scaffold
**That** enables instant iteration between Rust code and browser visualization
**Unlike** manually configuring wasm-pack, Vite, and TypeScript bindings separately
**Our solution** provides a single `npm run dev` command that builds WASM and serves the app with hot reload

---

Developers can now start building Physicall simulations with zero configuration. After cloning the repository, running `npm run dev` compiles the Rust code to WebAssembly, generates TypeScript bindings, and serves a local development server. Changes to Rust code trigger automatic rebuilds, and `console_log!` statements from Rust appear directly in the browser's developer console—making debugging seamless across the WASM boundary.

The environment is intentionally minimal: a working build pipeline, a canvas element ready for WebGPU, and logging connectivity. This foundation ensures all subsequent milestones (rendering, compute shaders, physics) have a stable base to build upon.

## FAQ

### Customer Experience

**Q: How does a developer start working on the project?**
A: Clone the repo, run `npm install` in the workspace root, then `npm run dev`. The browser opens to localhost showing the app. No additional setup required.

**Q: What does the developer see when the app loads successfully?**
A: A webpage with a canvas element (initially blank or showing a placeholder color). The browser console shows a "WASM initialized" log message from Rust, confirming the Rust-to-browser connection works.

**Q: How does a developer know their Rust code changes are working?**
A: They modify Rust code, save the file, and the wasm-pack build runs automatically. After rebuild completes, refreshing the browser shows the changes. Console logs from Rust appear in browser devtools.

**Q: What happens if the Rust code fails to compile?**
A: The wasm-pack build fails with compiler errors displayed in the terminal. The browser continues showing the last successful build until the error is fixed.

### Scope & Non-Goals

**Q: What is explicitly NOT included in E0.1?**
A:
- No WebGPU initialization (that's E0.2)
- No rendering (that's E0.3)
- No TypeScript UI components beyond basic HTML
- No hot module replacement for Rust (full rebuild on change is acceptable)

**Q: What's the minimal version that delivers the core benefit?**
A:
1. `wasm-pack build` produces a working `.wasm` file
2. Vite dev server imports and instantiates the WASM module
3. A Rust function can log to browser console

**Q: What would make us cut scope further?**
A: If TypeScript bindings prove complex, we could use raw WASM imports initially and add wasm-bindgen ergonomics later. The core value is "Rust compiles, browser runs it."

### Technical Constraint FAQs

**Q: What existing system capabilities does this depend on?**
A:
- Rust toolchain (rustup, cargo)
- wasm-pack CLI
- Node.js + npm
- A browser with WASM support (all modern browsers)

**Q: What new capabilities need to be built?**
A:
- Cargo workspace configuration with wasm32 target
- wasm-pack build configuration (Cargo.toml settings)
- Vite configuration to load WASM modules
- Basic HTML page with canvas element
- WASM loader TypeScript module

**Q: What's the simplest implementation that delivers the PR outcome?**
A:
- Single Rust crate with one exported function
- Vite with vite-plugin-wasm (or manual WASM loading)
- index.html with a `<canvas>` and `<script type="module">`
- main.ts that imports WASM and calls the init function

---

### Edge Cases & Error States

**Q: What happens if wasm-pack is not installed?**
A: Build script fails with clear error message: "wasm-pack not found. Install with: cargo install wasm-pack"

**Q: What happens if the browser doesn't support WASM?**
A: Extremely unlikely (all browsers since 2017 support it), but the WASM loader should catch and display a message.

**Q: What if npm packages fail to install?**
A: Standard npm error handling. No special mitigation needed—developer resolves like any npm project.

---

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
1. `wasm-pack build --target web` completes without errors
2. `npm run dev` serves the app at localhost
3. Browser console shows log output from Rust code
4. A new developer can complete setup in under 5 minutes (excluding install time)

**Q: What could go wrong post-setup?**
A:
- wasm-pack version incompatibilities (mitigate: pin version in docs)
- Vite WASM plugin issues (mitigate: test with current Vite version)

## Implementation Scope

### Current State → End State

| Current State | End State |
|---------------|-----------|
| Empty repository | Cargo workspace with physicall-core crate |
| No build process | `wasm-pack build` produces web-compatible WASM |
| No web frontend | Vite project serves HTML/TS at localhost |
| No Rust-browser connection | `console_log!` from Rust appears in browser devtools |

### User Stories

- [ ] As a developer, I can run `wasm-pack build` and get a working WASM module so that I have compiled Rust code ready for the browser
- [ ] As a developer, I can run `npm run dev` and see the app in my browser so that I can iterate on the project locally
- [ ] As a developer, I can use `console_log!` in Rust and see output in browser devtools so that I can debug WASM code

### Success Criteria

- [ ] `wasm-pack build --target web` in `crates/physicall-core` completes successfully
- [ ] `npm run dev` in workspace root starts Vite dev server on localhost
- [ ] Browser loads index.html and executes WASM module without errors
- [ ] A `console_log!("WASM initialized")` statement in Rust appears in browser console
- [ ] Project structure matches the layout defined in PROJECT_PLAN.md

### Known Compromises

- [ ] No hot reload for Rust changes—manual rebuild required (acceptable for learning project)
- [ ] No production build optimization—dev builds only for now
- [ ] Minimal error handling in WASM loader—assumes happy path

### Open Questions / Needs Research

- [ ] Which Vite plugin works best for WASM loading? (vite-plugin-wasm vs manual fetch/instantiate)
- [ ] Should we use wasm-bindgen's `console_log!` or a custom logging approach?
- [ ] What's the minimum wasm-pack/wasm-bindgen version needed for web target?
