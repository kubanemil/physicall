---

Users can now take full control of their physics simulations with the new control panel. Pause the simulation to examine particle positions, then resume to continue watching the physics unfold. Made a mess? Hit reset to restore the simulation to its initial state and try again.

The real power comes from the parameter sliders. Adjust gravity strength and watch particles float or plummet. Tweak particle count, change force multipliers, and experiment with different configurations—all while the simulation runs. Every change takes effect immediately, making it easy to explore "what if" scenarios and build intuition for how physical systems behave.

## FAQ

### Customer Experience

**Q: How does a user access these controls?**
A: The controls appear in a panel alongside the simulation canvas. They're always visible and accessible without interrupting the simulation view.

**Q: What does the pause/resume interaction look like?**
A: A single button toggles between "Pause" and "Resume" states. When paused, the simulation freezes but the user can still orbit the camera to examine the scene. A visual indicator (e.g., "PAUSED" overlay or dimmed state) shows when simulation is paused.

**Q: What happens when the user clicks reset?**
A: The simulation immediately returns to its initial state—particles return to their starting positions with initial velocities. If the simulation was paused, it remains paused after reset. The user's camera position is preserved.

**Q: How do the parameter sliders work?**
A: Each parameter has a slider with a labeled range (e.g., "Gravity: -20 to 20"). Dragging the slider updates the simulation in real-time. The current value is displayed next to the slider.

**Q: What parameters can be adjusted?**
A: For the particle system (M2):
- Gravity strength (real-time)
- Particle count (requires reset to take effect)
- Time scale / simulation speed (real-time)
- Boundary size (real-time)

**Q: Can parameter changes break the simulation?**
A: Sliders are constrained to valid ranges. Extreme values may produce chaotic but valid behavior. Parameters that could destabilize the simulation (like very high forces) will have sensible limits.

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- No presets or saved configurations (deferred to M5)
- No keyboard shortcuts (nice-to-have, not essential)
- No undo/redo for parameter changes
- No animation of reset (instant snap back)
- No per-particle editing (that's E3.2: Mouse Interaction)

**Q: What's the minimal version that delivers the core benefit?**
A: Pause/resume toggle + reset button + one working slider (gravity). This proves the JS→WASM→GPU uniform update pipeline works.

**Q: What would make us cut scope further?**
A: If the JS→WASM communication for parameter updates is complex, we could ship pause/reset first and add sliders in a follow-up.

**Q: What are we deferring to future iterations?**
A:
- Parameter presets (M5)
- Simulation type selector (M5)
- Saving/loading state (M5)
- Touch-friendly controls for mobile (out of scope per non-goals)

### Technical Constraint FAQs

**Q: What existing capabilities does this depend on?**
A:
- Working particle simulation (M2 complete)
- WASM↔JS interop already established
- GPU uniform buffers for simulation parameters

**Q: What new capabilities need to be built?**
A:
- TypeScript UI components (HTML/CSS)
- WASM-exported functions for pause/resume/reset
- Mechanism to update GPU uniform buffers from JS via WASM
- State management for "initial state" to enable reset

**Q: Are there performance constraints?**
A: Slider updates should not cause frame drops. Updates should go directly to GPU uniforms without re-uploading particle data.

**Q: What's the simplest implementation?**
A: Plain HTML elements (button, input[type=range]) styled with CSS. No framework needed. Direct calls to WASM-exported functions.

---

### Edge Cases & Error States

**Q: What happens if the user drags a slider very rapidly?**
A: Only the final value matters. We don't need to process every intermediate value—the next frame uses whatever the current value is.

**Q: What if reset is clicked while simulation is already at initial state?**
A: No-op. Button remains active, nothing visually changes.

**Q: What if particle count slider is changed mid-simulation?**
A: Particle count changes require reset to take effect. The slider shows the pending value, and a message indicates "Reset required to apply particle count change."

**Q: What happens to UI state on page refresh?**
A: All parameters reset to defaults. No persistence in V1.

---

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- User can pause, examine, and resume without issues
- Reset reliably returns to initial state
- Slider changes are reflected in simulation within same frame
- No frame rate degradation when adjusting parameters

**Q: What could go wrong post-launch?**
A:
- Slider ranges might feel wrong (too limited or too extreme)
- Reset might not capture all state (some drift remains)
- UI might obscure simulation on smaller screens

**Q: Are there compliance or security considerations?**
A: None. All computation is local, no data leaves the browser.

## Implementation Scope

### Current State → End State

| Current State | End State |
|--------------|-----------|
| Simulation runs continuously, cannot be paused | User can pause/resume simulation with a button |
| No way to restart, must refresh page | User can reset simulation to initial state |
| Parameters fixed at compile time | User can adjust gravity and other parameters via sliders |
| No visual feedback of simulation state | Clear indication when paused vs running |

### User Stories

- [ ] As a user, I can pause the simulation so that I can examine particle positions
- [ ] As a user, I can resume a paused simulation so that I can continue watching the physics
- [ ] As a user, I can reset the simulation so that I can start over with a fresh state
- [ ] As a user, I can adjust gravity strength via slider so that I can experiment with different forces
- [ ] As a user, I can see the current value of each parameter so that I know what settings I'm using
- [ ] As a user, I can tell whether the simulation is paused or running so that I understand the current state

### Success Criteria

- [ ] Pause button stops particle movement; resume continues from exact paused state
- [ ] Reset returns all particles to initial positions and velocities
- [ ] Gravity slider updates take effect within the same frame
- [ ] Controls are visible and usable alongside the simulation canvas
- [ ] No frame rate drop when rapidly adjusting sliders
- [ ] Camera orbit still works while simulation is paused

### Known Compromises

- [ ] No parameter persistence across page refreshes - acceptable for learning project, avoids localStorage complexity
- [ ] Particle count changes require reset - simplifies buffer management
- [ ] No undo/redo - adds significant complexity for minimal benefit in exploration context
- [ ] Plain HTML/CSS UI - no component framework, may look basic but functional
