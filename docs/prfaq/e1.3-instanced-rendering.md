> **Status**: Draft

## Press Release

**For** developers learning graphics programming and physics simulation
**Who** want to render thousands of objects (particles, spheres) without performance degradation
**The** Instanced Rendering system
**Is a** core rendering capability
**That** enables smooth 60fps rendering of 10,000+ particles using a single draw call
**Unlike** naive rendering where each object requires a separate draw call (causing massive GPU overhead)
**Our solution** uses WebGPU instanced rendering with GPU-resident buffers that are shared directly with compute shaders

---

Physicall now supports high-performance instanced rendering, enabling physics simulations with tens of thousands of particles at smooth frame rates. Users can watch complex particle systems, N-body simulations, and cloth physics without stuttering or frame drops.

The rendering system reads particle positions directly from GPU buffers—the same buffers written by physics compute shaders. This zero-copy approach eliminates the CPU-GPU data transfer bottleneck that typically limits particle system performance. Whether you're simulating 1,000 or 50,000 particles, the rendering cost remains nearly constant.

## FAQ

### Customer Experience

**Q: How does a user see this feature in action?**
A: Users will see it implicitly—when they run any particle simulation (gravity particles, N-body, cloth), thousands of objects render smoothly. The feature is invisible when working; users only notice its absence (stuttering, low FPS) if it weren't there.

**Q: What does the happy path look like?**
A:
1. User loads a simulation (e.g., 10,000 falling particles)
2. Physics compute shader updates particle positions in GPU buffer
3. Render pipeline reads same buffer and draws all particles in one instanced draw call
4. User sees smooth animation at 60fps with FPS counter confirming performance

**Q: What visual representation will instances have?**
A: Initially, particles will render as colored points or simple billboarded quads. Sphere mesh rendering (E1.2.3) is a separate story that builds on this foundation.

**Q: How does this interact with the camera system (E1.1)?**
A: The instanced rendering pipeline receives camera view/projection matrices via uniform buffers. Camera movement affects all instances uniformly through the vertex shader transformation.

### Scope & Non-Goals

**Q: What is explicitly NOT included in V1?**
A:
- Per-instance colors or materials (all instances same color initially)
- LOD (level of detail) based on distance
- Frustum culling (off-screen instances still processed)
- Dynamic instance count changes mid-frame
- Multiple instance types in single draw call

**Q: What's the minimal version that delivers the core benefit?**
A: A system that can render 10,000 identical point sprites from a GPU buffer in a single instanced draw call, reading positions written by a compute shader.

**Q: What would make us cut scope further?**
A: If GPU buffer sharing proves complex, we could start with CPU-uploaded instance data (slower but simpler), then optimize to GPU-only buffers.

**Q: What are we deferring to future iterations?**
A:
- Velocity-based coloring (M5 - E5.2.1)
- Multiple mesh types (spheres, cubes) in same scene
- Sorting instances for transparency
- GPU-driven indirect rendering

### Technical Constraint FAQs

**Q: What existing system capabilities does this depend on?**
A:
- WebGPU device and surface setup (E0.2)
- Basic render pipeline (E0.3)
- Camera matrices in uniform buffer (E1.1)

**Q: What new capabilities need to be built?**
A:
- Instance buffer layout and creation
- Vertex shader that reads per-instance data (position)
- Buffer usage flags allowing both STORAGE (compute) and VERTEX (render)
- Draw call using `draw_indexed_indirect` or `draw` with instance count

**Q: Are there performance, scale, or data constraints?**
A:
- Target: 10,000 instances at 60fps minimum
- Stretch: 100,000 instances at 30fps
- Instance data size: 16 bytes minimum (vec3 position + padding or vec4)
- GPU memory: ~1.6MB for 100K instances at 16 bytes each

**Q: What's the simplest implementation that delivers the PR outcome?**
A:
1. Create a GPU buffer with STORAGE | VERTEX usage
2. Compute shader writes positions to this buffer
3. Vertex shader reads instance_index and fetches position from buffer
4. Single `draw(vertices_per_instance, instance_count)` call

**Q: How will the instance buffer be structured?**
A: NEEDS RESEARCH - Options include:
- Array of vec4 (position.xyz + padding/scale)
- Struct with position, velocity, color
- Separate buffers for position vs. other attributes

### Edge Cases & Error States

**Q: What happens if instance count exceeds GPU limits?**
A: WebGPU has a max buffer size limit (typically 256MB+). At 16 bytes per instance, this allows millions of instances. We'll cap at a reasonable maximum (e.g., 1M) and log a warning if exceeded.

**Q: What happens if the GPU buffer isn't ready when rendering?**
A: The buffer is created at simulation init time. If somehow invalid, render nothing rather than crash. This is a programming error, not a user-facing state.

**Q: What happens with zero instances?**
A: Draw call with instance_count=0 is valid in WebGPU (draws nothing). No special handling needed.

### Business & Operational FAQs

**Q: How will we know if this is successful?**
A:
- Can render 10,000 particles at 60fps (measured via FPS counter from E3.3.1)
- Physics simulation (E2.2) works with rendered output
- No visible per-frame stuttering or hitching

**Q: What could go wrong post-launch?**
A:
- Browser WebGPU implementation differences causing buffer sharing issues
- Memory leaks if buffers aren't properly managed
- Unexpected performance cliffs at certain instance counts

**Q: Are there compliance or security considerations?**
A: No. This is client-side rendering with no user data involved.

## Implementation Scope

### Current State → End State

| Current State | End State |
|---------------|-----------|
| Can render a single triangle (E0.3) | Can render 10,000+ instances efficiently |
| Each object would need separate draw call | Single instanced draw call for all objects |
| No GPU buffer sharing between compute/render | Shared buffer written by compute, read by render |
| N/A | Instance positions come from GPU buffer, not CPU |

### User Stories

- [ ] **E1.3.1**: As a developer, I can render 10,000+ instances efficiently so that particle simulations run at interactive frame rates
- [ ] **E1.3.2**: As a developer, instance data comes from GPU buffer so that there's no CPU-GPU transfer per frame

### Success Criteria

- [ ] Rendering 10,000 point instances at 60fps on modern GPU
- [ ] Rendering 50,000 point instances at 30fps on modern GPU
- [ ] GPU buffer created with both STORAGE and VERTEX usage flags
- [ ] Vertex shader successfully reads per-instance position from buffer
- [ ] No CPU-side position data uploaded each frame (verified via no `write_buffer` calls in render loop)
- [ ] Single draw call renders all instances (verified via GPU profiler or code inspection)

### Known Compromises

- [ ] **No per-instance colors initially** - All instances render same color. Color variation deferred to E5.2.1 (velocity-based coloring)
- [ ] **No frustum culling** - Off-screen particles still consume GPU cycles. Acceptable for learning project; real engines would cull.
- [ ] **Fixed instance count per simulation** - Can't dynamically add/remove particles mid-simulation without buffer recreation. Acceptable for initial physics demos.

### Open Questions / Needs Research

- [ ] What's the optimal instance buffer layout for wgpu? (array of vec4 vs struct)
- [ ] How to properly declare buffer usage for both compute storage and vertex input in wgpu?
- [ ] Should we use `@builtin(instance_index)` or explicit instance buffer binding in vertex shader?
- [ ] What's the wgpu API for instanced draw calls? (`draw` vs `draw_indexed` with instance params)
- [ ] Are there any wgpu examples of compute-to-render buffer sharing we can reference?
