# Research: E3.2 Mouse Interaction

## Research Question

How should mouse interaction (drag particles, spawn/delete) be implemented in the current Physicall codebase? What existing infrastructure can be leveraged, and what new capabilities need to be built?

## Summary

The codebase already has substantial infrastructure for mouse interaction. Click-to-spawn is fully implemented using ray-plane intersection. Camera orbit controls via mouse drag are working. The main gaps for E3.2 are: (1) particle picking - finding which particle the user clicked on, (2) drag-to-move - applying forces to a grabbed particle, (3) delete functionality, and (4) hover feedback.

Key findings:
- **Ray casting is implemented** (`screen_to_world_ray` at lib.rs:165-206) and used for spawning
- **Particle data lives on GPU** with double-buffered storage, making CPU-side picking require either a copy or GPU readback
- **Input state tracking exists** (`InputState` struct) with drag detection and threshold-based click recognition
- **Particle struct** is 32 bytes with position, size, velocity - no "selected" flag exists currently
- **Spawning works** by writing directly to GPU buffers at `active_particle_count` offset

## Detailed Findings

### Existing Ray Casting Infrastructure

**File**: `crates/physicall-core/src/lib.rs:165-227`

Two helper functions exist for ray-based world interaction:

1. `screen_to_world_ray()` (lines 165-206)
   - Takes screen coordinates and canvas dimensions
   - Converts to NDC (-1 to 1)
   - Unprojects using inverse view-projection matrix
   - Returns `(ray_origin: Vec3, ray_direction: Vec3)`

2. `ray_plane_intersection()` (lines 210-227)
   - Computes ray-plane intersection point
   - Used for spawning particles at camera-facing plane

**Current usage** (lines 1684-1704):
- On click (not drag), screen coords are passed to `screen_to_world_ray`
- Ray intersects plane through camera target, normal facing camera
- Particle spawned at intersection point

### Particle Data Structure

**File**: `crates/physicall-core/src/lib.rs:521-545`

```rust
#[repr(C)]
struct Particle {
    position: [f32; 3],  // 12 bytes
    size: f32,           // 4 bytes
    velocity: [f32; 3],  // 12 bytes
    _padding: f32,       // 4 bytes (align to 32 bytes)
}
```

- Total size: 32 bytes per particle
- MAX_PARTICLES: 2,000 (pre-allocated buffer capacity)
- Active count tracked in `active_particle_count` field
- Double-buffered for ping-pong compute updates

## Architecture Notes

### Current Flow

```
Mouse Event (JS)
    ↓
InputState (Rust) - accumulates deltas
    ↓
render() polls InputState
    ↓
Camera updated OR spawn particle
    ↓
Compute pass (GPU) - updates particle physics
    ↓
Render pass (GPU) - draws particles
```

### Proposed Flow for Mouse Interaction

```
Mouse Event (Rust)
    ↓
InputState extended with:
    - hovered_particle_idx: Option<u32>
    - dragging_particle: Option<u32>
    ↓
render() checks:
    - If mousedown on particle → start drag
    - If dragging → update drag target position
    - If mouseup while dragging → release
    ↓
Compute pass:
    - If drag active, override dragged particle's position/velocity
    ↓
Render pass:
    - Highlight hovered/dragged particle (needs shader modification)
```

### Particle Picking Options

**Option A: CPU-side position copy**
- Maintain `Vec<[f32; 3]>` with particle positions
- Update after each compute pass (requires GPU readback or reconstruction)
- On click, iterate all positions and find nearest to ray

**Option B: GPU readback on demand**
- Add `MAP_READ` to buffer usage
- On click, map buffer and read positions
- Asynchronous - may have latency

**Option C: Compute-based picking**
- Create picking compute shader
- Pass ray origin/direction as uniforms
- Each particle checks if ray intersects its sphere
- Write hit particle index to output buffer
- Most complex but potentially most performant for large counts

**Recommendation**: Option A is simplest for 2,000 particles. With 32 bytes * 2,000 = 64KB, keeping a CPU copy is negligible overhead.

### Drag Force Application

Two approaches:

**Force-based**: Apply strong force toward cursor position
- More physically realistic
- Particle has momentum when released
- Implementation: Add drag force to acceleration in compute shader

**Position-based**: Teleport particle to cursor position each frame
- Simpler, more direct control
- No inertia on release (feels wrong for physics sim)
- Implementation: Skip physics for dragged particle, set position directly

**Recommendation**: Force-based feels better for a physics simulation. Tune force magnitude for responsiveness.

### Delete Implementation

Options:
- Swap-with-last: Move last particle to deleted slot, decrement count
  - O(1) but changes particle ordering
  - Requires writing to GPU buffer
- Mark as deleted: Add flag to Particle struct
  - Compute shader skips deleted particles
  - Keeps ordering but wastes space

**Recommendation**: Swap-with-last is simpler and particle ordering doesn't matter in N-body sim.

## Open Questions

1. **Hover feedback mechanism**: Should hovering be handled on CPU (change cursor) or GPU (highlight in shader)?
   - CPU: Needs continuous picking, may impact performance
   - GPU: Needs picking result passed to shader, adds complexity

2. **Camera vs particle drag priority**: If clicking on a particle, should camera orbit be disabled?
   - Current: All left-drags orbit camera
   - Proposed: Click-on-particle drags particle, click-on-background orbits camera

3. **Drag plane**: Should dragging be constrained to a plane?
   - Current spawn uses camera-facing plane through target
   - Same plane could work for dragging
   - Alternatively, drag in screen XY mapped to world

4. **GPU buffer recreation**: Current buffers lack `MAP_READ`. Should we:
   - Recreate with `MAP_READ` (slight perf cost)
   - Add staging buffer for readback
   - Go with CPU copy approach
