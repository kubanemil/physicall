# Research: E4.1 - Collision Detection

## Research Question

What is the current state of the codebase relevant to implementing particle-particle collision detection with spatial hashing? What existing infrastructure exists, what needs to be added, and what are the key integration points?

## Summary

The Physicall project currently implements an N-body gravitational simulation with 200 particles running on the GPU via a single compute shader (`particle_compute.wgsl`). Particles attract each other gravitationally but pass through one another — there is no collision detection or response. The compute pipeline uses a double-buffered ping-pong pattern with a `Particle` struct (position, size, velocity) stored in two storage buffers, and a `SimParams` uniform buffer updated each frame from Rust.

To implement E4.1, the compute shader needs two additions: (1) a collision detection and response pass that detects overlapping particles and applies impulse-based separation, and (2) a spatial hash data structure on the GPU to avoid O(n²) pair-wise checks. The existing buffer infrastructure supports this — particle buffers already have `STORAGE | COPY_DST | COPY_SRC` usage flags — but new GPU buffers will be needed for the spatial hash (cell arrays, particle indices, atomic counters). The compute pipeline currently uses a single bind group with 3 bindings; collision will require either expanding this or adding a second bind group for hash data.

The PRFAQ (`docs/prfaq/e4.1-collision-detection.md`) defines the scope: impulse-based elastic collision, single pass per frame, fixed cell size (2x particle radius), no friction/rotation, no CCD. Success criteria include 1000+ colliding particles at >30 FPS with spatial hashing reducing complexity to approximately O(n).

## Detailed Findings

### Current Physics Pipeline

The entire physics simulation runs in a single compute shader dispatched once per frame.

**Compute shader** (`shaders/particle_compute.wgsl`):
- Entry point: `main` with `@workgroup_size(256)` (line 28)
- Bindings: `particles_in` (read-only storage, binding 0), `particles_out` (read-write storage, binding 1), `params` (uniform, binding 2)
- Algorithm: O(n²) N-body gravitational force calculation (lines 41-56), followed by semi-implicit Euler integration (lines 67-69)
- Drag override: if particle is being dragged, replaces acceleration with spring force toward cursor target (lines 59-64)

**Rust compute setup** (`crates/physicall-core/src/lib.rs`):
- Compute bind group layout: 3 entries — storage read-only, storage read-write, uniform (lines 1319-1357)
- Pipeline layout: single bind group layout (lines 1360-1365)
- Shader loaded via `include_str!` (lines 1368-1373)
- Dispatch: `ceil(active_particle_count / 256)` workgroups (line 1774)
- Only dispatched when not paused (line 1766)

### Particle Data Structure

**Rust Particle struct** (`lib.rs:594-607`):
```rust
struct Particle {
    position: [f32; 3],  // 12 bytes
    size: f32,           //  4 bytes
    velocity: [f32; 3],  // 12 bytes
    _padding: f32,       //  4 bytes
}                        // Total: 32 bytes
```

**WGSL Particle struct** (`particle_compute.wgsl:4-9`):
```wgsl
struct Particle {
    position: vec3f,
    size: f32,
    velocity: vec3f,
    _padding: f32,
}
```

Key observations:
- `size` field exists on every particle (currently `PARTICLE_SIZE = 0.03` for all)
- No mass field — N-body assumes unit mass
- 32-byte alignment is cache-friendly
- The `size` field can serve as collision radius directly

### SimParams Uniform

**Rust struct** (`lib.rs:620-633`):
```rust
struct SimParams {
    delta_time: f32,
    gravitational_constant: f32,
    damping: f32,
    particle_count: u32,
    softening_sq: f32,
    drag_strength: f32,
    dragged_particle_idx: i32,
    hovered_particle_idx: i32,
    drag_target: [f32; 3],
    _padding: f32,
}
```
- 48 bytes total
- Updated every frame via `queue.write_buffer()` (lines 1736-1740)
- Will need new fields for collision parameters (e.g., restitution coefficient, cell size, grid dimensions)

### Buffer Architecture

**Particle buffers** (`lib.rs:1289-1316`):
- Two buffers (ping-pong), pre-allocated for `MAX_PARTICLES = 2,000` (64 KB each)
- Usage flags: `STORAGE | VERTEX | COPY_DST | COPY_SRC`
- Both buffers initialized with same data on creation
- Both buffers updated on spawn (`lib.rs:1587-1602`), delete (`lib.rs:1642-1659`), and direct position update (`lib.rs:1686-1695`)

**Compute bind groups** (`lib.rs:1388-1425`):
- Two bind groups for ping-pong:
  - Group 0: reads buffer[0], writes buffer[1]
  - Group 1: reads buffer[1], writes buffer[0]
- Both bind the same `sim_params_buffer` at binding 2

**Compute dispatch** (`lib.rs:1761-1776`):
```rust
let read_idx = (self.frame_index % 2) as usize;
let write_idx = ((self.frame_index + 1) % 2) as usize;
// ...
compute_pass.set_bind_group(0, &self.compute_bind_groups[read_idx], &[]);
let workgroup_count = (self.active_particle_count + 255) / 256;
compute_pass.dispatch_workgroups(workgroup_count, 1, 1);
```

### Render Pipeline Integration

**Particle rendering** (`lib.rs:1816-1824`):
- Particles rendered as instanced quads using the write buffer from compute
- When paused, reads from `read_idx`; when running, reads from `write_idx`
- Point shader (`shaders/point.wgsl`) reads SimParams for hover/drag highlighting
- Particle buffer serves dual purpose: STORAGE for compute, VERTEX for render

**Render bind group for points** shares `sim_params_buffer` with compute:
- Compute: binding 2 at group 0
- Point render: binding 1 at group 0 (separate bind group layout)

### CPU-Side Particle Tracking

**Particle positions mirror** (`lib.rs:1548`):
```rust
particle_positions: Vec<Vec3>
```
- Maintained on CPU for ray-based picking (hover, drag, delete)
- Updated on spawn, delete, and direct position update
- Used by `pick_particle()` (`lib.rs:1604-1626`) for ray-sphere intersection
- Currently NOT updated from GPU readback — positions diverge from GPU after first frame unless manually updated

**Implication for collision**: CPU mirror is already stale after first compute frame. Collision response on the GPU will further change positions. The CPU mirror is only used for picking, which is approximate — this is acceptable.

### Existing Boundary Collision

There is NO floor/boundary collision in the current codebase. The PRFAQ and E2.2 plan mention floor collision at y=-2.0, but the current `particle_compute.wgsl` does not implement it. The N-body simulation (E2.3) replaced the gravity+floor simulation (E2.2) and dropped floor collision.

### WGSL Capabilities Relevant to Collision

From the current shader and WGSL spec:
- `atomicAdd`, `atomicMax` etc. available for `atomic<u32>` and `atomic<i32>` types
- Storage buffers support `read_write` access mode
- Workgroup shared memory available via `var<workgroup>`
- No dynamic memory allocation — all buffer sizes fixed at pipeline creation
- Maximum storage buffer binding size: device-dependent (typically 128MB+)

## Architecture Notes

### Current Frame Flow
```
Frame N:
  1. CPU: Update SimParams → queue.write_buffer(sim_params_buffer)
  2. CPU: Update CameraUniform → queue.write_buffer(camera_buffer)
  3. GPU: Compute pass (if not paused)
     - Read particles_in[frame_index % 2]
     - Calculate N-body forces + drag
     - Integrate (semi-implicit Euler)
     - Write particles_out[(frame_index + 1) % 2]
  4. GPU: Render pass
     - Draw lines, particles (from write buffer), spheres
  5. CPU: frame_index += 1 (if not paused)
```

### Integration Points for Collision

Collision detection fits into step 3, either:
- **Option A**: Added to the existing compute shader after N-body forces, before integration
- **Option B**: As a separate compute pass after the N-body pass

Spatial hashing requires:
- **New GPU buffers**: cell counters, particle index lists, cell start/end arrays
- **New compute passes**: (1) clear hash, (2) assign particles to cells, (3) prefix sum for compaction, (4) collision detection + response
- **New bind group entries** or a **second bind group** for hash data

### Buffer Budget

Current GPU memory usage:
- 2x particle buffers: 2 × 64 KB = 128 KB
- Camera uniform: 64 bytes
- SimParams uniform: 48 bytes
- Line vertices: ~288 bytes
- Quad vertices + indices: ~48 bytes
- Sphere mesh: ~10 KB
- Sphere instances: ~256 bytes

Spatial hash estimate (for 2,000 particles, cell size = 2 × PARTICLE_SIZE = 0.06):
- Cell counter buffer: grid_size³ × 4 bytes (e.g., 128³ = 8 MB — too large for uniform grid)
- Better approach: hash table with fixed bucket count (e.g., 4096 buckets × 4 bytes = 16 KB)
- Particle index buffer: MAX_PARTICLES × 4 bytes = 8 KB
- Cell start/end arrays: num_buckets × 8 bytes = 32 KB
- Total hash overhead: ~56 KB

## Open Questions

1. **Spatial hash vs. uniform grid**: A hash table avoids allocating a full 3D grid. For particles in a bounded region, which is more practical on the GPU?
2. **Atomic operations in WGSL**: WGSL supports `atomicAdd` on `atomic<u32>` in storage buffers. Are there performance concerns with heavy atomic contention when many particles hash to the same cell?
3. **Multi-pass vs. single-pass**: The hash build requires (a) counting particles per cell, (b) prefix sum, (c) scattering particles to sorted order. This is at least 3 dispatches. Can it be simplified?
4. **Collision + N-body in same pass**: Currently the N-body loop is O(n²). Adding collision response after forces but before integration keeps the architecture clean. But collision needs neighbor data from the spatial hash. Should the N-body also use the spatial hash to reduce to O(n log n)?
5. **Restitution coefficient**: PRFAQ suggests 0.8 (slightly inelastic). Should this be a constant or a SimParams field for future UI control?
6. **Floor collision**: The PRFAQ mentions "existing floor boundary" but none exists in the current code. Should E4.1 add floor collision, or is that separate?
