# Research: E1.3 Instanced Rendering

## Research Question

How to implement efficient instanced rendering in wgpu/WebGPU that can render 10,000+ particles at 60fps, with GPU buffers shared between compute shaders and render pipelines?

## Summary

The physicall codebase already has a working foundation for instanced rendering with two implementations:

1. **Point Instancing** (`lib.rs:368-470`): Renders 200 points using instanced quads with per-instance position, size, and color.
2. **Sphere Instancing** (`lib.rs:472-695`): Renders 8 spheres using instanced icosphere meshes with per-instance position, radius, and color.

Both use `wgpu::VertexStepMode::Instance` for per-instance data, which is the correct approach. The current implementation supports the instancing pattern needed for E1.3, but instance buffers are currently created with `BufferUsages::VERTEX` only. For compute-to-render buffer sharing (needed for physics simulation), buffers need `BufferUsages::STORAGE | BufferUsages::VERTEX` combined flags.

The key changes needed are:
1. Add `STORAGE` usage flag to instance buffers
2. Create bind groups for compute shader access
3. Implement compute shaders that write to shared buffers
4. Use double-buffering pattern to avoid read-write conflicts

## Detailed Findings

### Existing Instancing Implementation

#### Point Instance Structure (`lib.rs:404-428`)

```rust
#[repr(C)]
#[derive(Copy, Clone, Debug, bytemuck::Pod, bytemuck::Zeroable)]
struct PointInstance {
    position: [f32; 3],
    size: f32,
    color: [f32; 3],
    _padding: f32,  // Align to 32 bytes
}

impl PointInstance {
    const ATTRIBS: [wgpu::VertexAttribute; 3] = wgpu::vertex_attr_array![
        1 => Float32x3,  // world_pos @ location(1)
        2 => Float32,    // size @ location(2)
        3 => Float32x3,  // color @ location(3)
    ];

    fn desc() -> wgpu::VertexBufferLayout<'static> {
        wgpu::VertexBufferLayout {
            array_stride: std::mem::size_of::<PointInstance>() as wgpu::BufferAddress,
            step_mode: wgpu::VertexStepMode::Instance,  // Per-instance, not per-vertex
            attributes: &Self::ATTRIBS,
        }
    }
}
```

### Buffer Usage Flags for Compute-Render Sharing

For E1.3.2 (instance data from GPU buffer with no CPU transfer), the buffer creation needs:

```rust
// Required for compute-to-render buffer sharing
let shared_instance_buffer = device.create_buffer(&wgpu::BufferDescriptor {
    label: Some("Shared Particle Buffer"),
    size: instance_data_size,
    usage: wgpu::BufferUsages::STORAGE  // Compute shader write access
         | wgpu::BufferUsages::VERTEX   // Render pass read access
         | wgpu::BufferUsages::COPY_DST, // Optional: CPU initialization
    mapped_at_creation: false,
});
```

### Double-Buffering Pattern (Boids Example)

For physics simulation where compute reads and writes particle data:

```rust
// Create two buffers, alternate between them each frame
let particle_buffers: [wgpu::Buffer; 2] = [
    create_shared_buffer(&device, &initial_data),
    create_shared_buffer(&device, &initial_data),
];

// Frame N:
//   - Compute pass reads from buffer[0], writes to buffer[1]
//   - Render pass reads from buffer[0] as vertex buffer
// Frame N+1:
//   - Compute pass reads from buffer[1], writes to buffer[0]
//   - Render pass reads from buffer[1] as vertex buffer

let frame_idx = frame_count % 2;
let read_buffer = &particle_buffers[frame_idx];
let write_buffer = &particle_buffers[(frame_idx + 1) % 2];
```

### Compute Shader Bind Group Layout

For compute shader to write to instance buffer:

```rust
let compute_bind_group_layout = device.create_bind_group_layout(&wgpu::BindGroupLayoutDescriptor {
    label: Some("Compute Bind Group Layout"),

        wgpu::BindGroupLayoutEntry {
            binding: 0,

                has_dynamic_offset: false,
                min_binding_size: None,
            },
            count: None,
        },
        // Simulation params (uniform)
        wgpu::BindGroupLayoutEntry {
            binding: 1,
            visibility: wgpu::ShaderStages::COMPUTE,
            ty: wgpu::BindingType::Buffer {
                ty: wgpu::BufferBindingType::Uniform,
                has_dynamic_offset: false,
                min_binding_size: None,
            },
            count: None,
        },
    ],
});
```

### Command Encoder Ordering

Synchronization is automatic when using same encoder:

```rust
let mut encoder = device.create_command_encoder(&Default::default());

// 1. Compute pass writes particle positions
{
    let mut compute_pass = encoder.begin_compute_pass(&Default::default());
    compute_pass.set_pipeline(&compute_pipeline);
    compute_pass.set_bind_group(0, &compute_bind_group, &[]);
    compute_pass.dispatch_workgroups((particle_count + 255) / 256, 1, 1);
    // Pass automatically ends when dropped
}

// Implicit memory barrier inserted by wgpu here

// 2. Render pass reads particle positions
{
    let mut render_pass = encoder.begin_render_pass(&render_pass_descriptor);
    render_pass.set_pipeline(&render_pipeline);
    render_pass.set_vertex_buffer(0, quad_vertex_buffer.slice(..));
    render_pass.set_vertex_buffer(1, particle_buffer.slice(..));  // Same buffer!
    render_pass.draw_indexed(0..6, 0, 0..particle_count);
}

queue.submit(std::iter::once(encoder.finish()));
```

### Memory Layout Considerations

#### WGSL Alignment Rules

| Type | Alignment | Size |
|------|-----------|------|
| f32, i32, u32 | 4 bytes | 4 bytes |
| vec2 | 8 bytes | 8 bytes |
| vec3 | **16 bytes** | 12 bytes |
| vec4 | 16 bytes | 16 bytes |

**Important**: vec3 has 16-byte alignment but only 12 bytes of data. This causes padding issues.

#### Current Layout Analysis

The existing `PointInstance` and `SphereInstance` structs are well-designed:
- 32 bytes total (power of 2, cache-friendly)
- Explicit `_padding` field handles alignment
- `#[repr(C)]` ensures predictable layout

For compute shader compatibility, the WGSL struct must match exactly:

```wgsl
struct Particle {
    position: vec3f,    // 12 bytes
    size: f32,          // 4 bytes (offset 12)
    color: vec3f,       // 12 bytes (offset 16)
    _padding: f32,      // 4 bytes (offset 28)
    // Total: 32 bytes
}

@group(0) @binding(0) var<storage, read_write> particles: array<Particle>;
```

### Performance Characteristics

#### Achievable Performance

| Instance Count | Target FPS | Notes |
|----------------|------------|-------|
| 10,000 | 60 fps | E1.3 target |
| 50,000 | 30 fps | E1.3 stretch goal |
| 100,000 | 15-30 fps | With optimizations |

#### Optimization Techniques

1. **Single Draw Call**: All instances in one `draw_indexed` call
2. **GPU-Resident Data**: No CPU-GPU transfer per frame
3. **Double Buffering**: Hides synchronization latency
4. **256-Thread Workgroups**: Standard compute dispatch size
5. **Cache-Aligned Structs**: 32-byte instance data

### Two Approaches for Vertex Shader

#### Approach 1: Explicit Instance Attributes (Current)

```wgsl
struct InstanceInput {
    @location(1) world_pos: vec3f,
    @location(2) size: f32,
    @location(3) color: vec3f,
}

@vertex
fn vs_main(quad: QuadInput, instance: InstanceInput) -> VertexOutput {
    // Direct access to instance data
}
```

**Pros**: Type-safe, readable, well-supported
**Cons**: Requires vertex buffer binding

#### Approach 2: Storage Buffer + @builtin(instance_index)

```wgsl
@group(0) @binding(1) var<storage> particles: array<Particle>;

@vertex
fn vs_main(
    @location(0) quad_pos: vec2f,
    @builtin(instance_index) idx: u32
) -> VertexOutput {
    let particle = particles[idx];
    // Access via storage buffer indexing
}
```

**Pros**: Same buffer for compute and render, no separate binding
**Cons**: Slightly more indirection, requires bind group changes

**Recommendation**: Keep current explicit attributes approach. It's cleaner and the buffer sharing works via dual usage flags (`STORAGE | VERTEX`).

## Open Questions

### Answered by Research

1. **Q: What's the optimal instance buffer layout for wgpu?**
   **A**: Array of structs with 32-byte alignment. Current `PointInstance` and `SphereInstance` layouts are correct.

2. **Q: How to declare buffer usage for both compute and render?**
   **A**: Use `BufferUsages::STORAGE | BufferUsages::VERTEX | BufferUsages::COPY_DST`

3. **Q: Should we use @builtin(instance_index) or explicit attributes?**
   **A**: Keep explicit attributes. They're cleaner and work with dual-usage buffers.

4. **Q: What's the wgpu API for instanced draw calls?**
   **A**: `draw_indexed(indices: Range<u32>, base_vertex: i32, instances: Range<u32>)`

5. **Q: Are there wgpu examples of compute-to-render buffer sharing?**
   **A**: Yes, the official wgpu "boids" example demonstrates this pattern with double-buffering.
